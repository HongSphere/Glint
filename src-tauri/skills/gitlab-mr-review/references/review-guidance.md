# MR 评审要点与分级标准

## 输出分级

- **🔴 高**：会导致错误结果、数据污染、空数据返回、竞态损坏、公开接口行为变更是实质 bug / 缺口。给出：位置、触发场景、具体修复建议。
- **🟠 中**：明确的隐患、名不副实、文档与实现不符、需人工确认的风险点。
- **🟡 低/建议**：健壮性、性能、命名、测试缺口、风格。可用表格收拢。
- 最后列 **✅ 已验证无问题的点**（写明核实依据）——提升可信度，避免"只挑毛病"。

## 常用检查项（按主题）

### 缓存 / Redis
- 缓存 key 构造与 CacheManager 配置是否一致：key 前缀、key 序列化器（String vs JDK vs JSON）、TTL 解析（如 `name#ttl`，`#0` 常表示不设过期）。
- **缓存缺失 + 刷新失败时的兜底**：是否回退数据库，还是悄悄返回空/旧数据？"读取异常"≠"key 缺失"。
- 直接读 Redis 字节再手动反序列化（ByteArrayCodec + 序列化 pair）的路径是否被单测覆盖，还是只靠集成验证。
- 返回共享缓存对象给调用方：是否可能被 mutate 污染全局快照。
- Redis 故障时是否每个请求都直查 DB（雪崩风险）。

### 分布式锁 / 并发
- 锁租约（lease）是否大于"拿锁后操作"耗时；无 watchdog 续期时，慢操作期间锁过期 → 重复加载 / 旧写覆盖新写。
- 锁等待超时后的行为是否安全（保留旧值 vs 并发写）。
- 异步刷新事件是否合并/去抖；N 次写是否触发 N 次全量刷新。

### 租户隔离（MyBatis-Plus）
- 全局快照/字典加载若走 MyBatis-Plus，会被 `TenantLineInnerInterceptor` 拦截。看 `TenantLineHandler.ignoreTable`：
  - 租户上下文为空 → 查全量；非空 → 仅名单内表过滤。
- 判断目标表是否可能被租户过滤：查表结构有无 `tenant_id` 列（没有就不可能被过滤，否则 SQL 直接报错）。
- 请求线程触发刷新（带租户上下文）vs 异步线程（无上下文）路径是否一致；建议加载全局数据时显式忽略租户（如 `@InterceptorIgnore(tenantLine="true")`）。

### 事务 / 事件
- 写方法是否 `@Transactional`；事件应在事务提交后触发（`@TransactionalEventListener(AFTER_COMMIT)`），回滚不得刷新。
- 校验（读）与写入之间的竞态窗口是否有约束兜底。

### 行为变更
- 重构后公开接口语义是否变化（如 `list(level<3)` 返回层级变深）。搜索调用方确认影响面。
- 远程依赖是否真的移除（`RemoteDistService` 等 Feign import 是否彻底消失）。

### 测试 / 文档一致性
- 文档宣称的单测覆盖，MR 里是否真的存在。
- 最脆弱路径（字节级反序列化、锁竞态、事务事件）是否被测试覆盖。

### 无关改动
- 与 MR 主题无关的一次性任务（如硬编码时间窗的补偿 job）是否混入，应拆分/参数化。

### 安全
- 新增 POST/写接口是否鉴权；行内评论/注记发布以登录账号身份进行，先确认用户认可。

## 核实技巧
- 大改前先验证关键前提（缓存 key 是否一致、序列化 round-trip、租户是否过滤、远程调用是否真移除），避免评审结论建立在错误假设上。
- 用 raw API 拉源码分支文件核对 diff 之外的上下文（辅助方法、配置类、实体字段）。
- 回写前重拉 diff 做 `shasum` 对比，确认评审对象未过期。
